Repo is a monorepo: FastAPI backend (`app/`) plus a Next.js 16 App Router + TypeScript frontend (`web/`), using `@tanstack/react-query` for data fetching and a hand-rolled `fetch` wrapper (`web/lib/api.ts`) for the API client — no axios/swr.

**Auth/token storage — UPDATED by FT-43, do not flag localStorage/bearer anymore:** FT-35 originally stored a JWT in `localStorage`; FT-43 migrated this to an httpOnly `session` cookie + readable `csrf_token` cookie (double-submit). `web/lib/api.ts` now sends `credentials: 'include'` on every request and attaches `X-CSRF-Token` (read from the `csrf_token` cookie) on mutating requests. See [[project_httponly_cookie_csrf]] for the full design. There is no client-readable token anywhere in `web/` as of FT-43 — this closes the XSS-token-theft tradeoff noted in the original FT-35 memory.

**401 handling pattern:** `web/lib/api.ts` uses a module-level `unauthorizedHandled` boolean to dedupe concurrent 401s into a single hard redirect (`window.location.assign('/login')`), reset via `resetUnauthorizedGuard()` on fresh login. Requests can opt out via a `skipAuthRedirect` flag (used by `AuthProvider`'s mount-time hydration in `web/lib/auth.tsx`) so a stale/invalid session on first load settles to logged-out quietly instead of redirecting.

**Fixed in FT-35:** `hydrate()` in `web/lib/auth.tsx` used to treat *any* thrown error from `/users/me` as "invalid session". Now only a confirmed `ApiError` with `status === 401` clears state; other failures (network/5xx) resolve to `user: null` for that load without clearing anything persistent (moot now anyway since there's no client-side token to clear).

**Fixed in FT-36:** `AuthProvider.login()` used to resolve successfully even when post-login hydration (`GET /users/me`) returned `null`, silently leaving `user: null` with no error surfaced. Now throws `Error('Login succeeded but failed to load user profile')` when hydration comes back null, so callers (the login page) can react. Covered by a test in `web/lib/auth.test.tsx`.

**ESLint convention:** project uses `semi: ['error', 'never']` (no semicolons) in `web/eslint.config.mjs` as of FT-35 — new files should follow no-semicolon style.

**FT-36 — first page + `ui/` primitives:** `web/app/login/page.tsx` (react-hook-form + zod) and `web/components/ui/{Button,Input,Card}.tsx`. Notable patterns to check on future diffs that touch these:
- Login error branching: `err instanceof ApiError && err.status === 401` → "Incorrect username or password", else → generic "Something went wrong". This correctly catches both real 401s and the FT-36 `auth.tsx` plain-`Error` throw (non-`ApiError`, falls to generic branch) — reasonable, but note network/`TypeError` failures also land in the generic branch indistinguishably from "backend returned 500."
- `Input.tsx`/`Button.tsx` dropped `forwardRef` in favor of React 19's ref-as-prop (`ref` included directly in the props type) — this is the current convention for new components, not a regression.
- **Fixed in commit `d714a64`, verified by code-quality-reviewer:** `Input.tsx` now has `aria-invalid`/`aria-describedby` wired to a matching `role="alert"` error `<p id>`; login page's `formError` `<p>` also has `role="alert"`; `Button` defaults `type` to `'button'`; `isLoading` now shows an `aria-hidden` spinner alongside the label instead of replacing it (no layout shift). Do not re-flag these three.
- Residual minor items (confirmed still present as of the full-branch review on 2026-11-04, still low priority): `Input.tsx` spreads `{...rest}` *after* its computed `aria-invalid`/`aria-describedby`, so a future caller passing those props directly would silently override the component's own a11y linkage — reorder the spread before the computed attrs if this comes up again. Also, `login/page.tsx`'s `onSubmit` has no guard against a second submit fired via Enter-key while `isSubmitting` is already true (Button's `disabled` only blocks click, not native form resubmission) — react-hook-form's `isSubmitting` flips asynchronously via re-render, so a fast double-Enter in the password field could in theory fire `onSubmit` twice before the button disables.
- `Input.tsx`'s id-fallback (`label.toLowerCase().replace(/\s+/g, '-')`, used only when neither `id` nor `name` is passed) would produce duplicate DOM ids if two inputs share a label text and neither prop is supplied — not triggered today (every current usage passes `name` via `register()`), but worth checking if a future form adds unlabeled-by-name inputs.
- `.env.local.example`'s `NEXT_PUBLIC_API_URL` was changed from `http://127.0.0.1:8000` to `http://localhost:8000` in FT-36 — confirmed benign (backend binds `127.0.0.1` which `localhost` resolves to; CORS origin is already `http://localhost:3000` in `app/config/settings.py`), just a dev-env consistency tweak, not a defect.

**FT-37 — authed app shell (`(app)` route group):** `web/app/(app)/layout.tsx` (client-side guard: skeleton while `loading`, `useEffect`-driven `router.replace('/login')` when `user === null`, else renders `AppShell`), `web/components/nav/{AppShell,Sidebar,TopBar,MobileDrawer,navItems}.tsx`, `web/components/ui/Skeleton.tsx` (+ `AppShellSkeleton`). Added `lucide-react` (real package, versioned 1.x — not a typo, confirmed via npm). `web/app/(app)/page.tsx` sets `export const instant = false` — this is a real Next.js 16 segment-config field (`AppSegmentConfig.instant`, confirmed in `next/dist/build/segment-config/app/app-segment-config.d.ts`), used here because the layout's client-side auth gate means the segment can't produce a statically-verifiable instant-nav shell. Lint/build/test all pass clean on this diff.
- **Duplication worth flagging in future diffs that touch nav:** `Sidebar.tsx` and `MobileDrawer.tsx` each independently reimplement the exact same nav-link-map-with-active-state block (identical Tailwind className ternary) and the exact same logout `<button>` markup — same JSX/classNames copy-pasted across both files rather than sharing a `NavLinks`/`LogoutButton` sub-component. Given the project already extracted `NAV_ITEMS` as a shared source of truth, extracting the link-rendering and logout-button JSX too would be a natural, low-risk follow-up if this area is touched again.
- `AppShell.tsx`'s `handleLogout` has no try/catch around `await logout()` — if logout rejects, it's an unhandled promise rejection with no user-facing feedback. Low severity for a pure-navigation action but note if logout error handling is added elsewhere later.
- Backdrop `<div onClick={onClose}>` in `MobileDrawer.tsx` has no keyboard handler/role, which could trip `jsx-a11y/no-static-element-interactions` or `click-events-have-key-events` — confirmed these rules are **not** enabled in `web/eslint.config.mjs` (just `eslint-config-next/core-web-vitals` + `typescript` + quote/semi overrides), so lint stays clean; not a defect under current config, just worth knowing if a11y lint rules are ever tightened.

See also [[project_rbac_patterns]] for backend-side role model that this frontend will eventually need to respect in UI gating (no role-based UI logic yet — `User.role` is fetched but unused beyond display).
