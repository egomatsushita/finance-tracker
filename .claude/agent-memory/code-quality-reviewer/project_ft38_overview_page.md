Full-branch review on 2026-11-10 (10 commits, `main...HEAD`). Backend touches `app/repositories/transaction.py`, `app/schemas/params.py`, `app/schemas/transaction.py`, plus a new data-seed migration. Frontend builds the real `(app)/` overview dashboard (`OverviewClient.tsx`, `CategoryBarChart.tsx`, `IncomeExpenseTrendChart.tsx`, `lib/queries.ts`, `lib/format.ts`, `lib/categoryIcons.tsx`) using `/transactions/summary` and `/transactions/` endpoints that **already existed on `main` before this branch** (`app/routers/transaction.py` `read_transaction_summary` + `TransactionService.get_summary` are pre-existing, not part of this diff — do not re-review them here unless they show up in the diff stat).

Key observations, none blocking:

1. **Seed migration `2026_11_10_0900-a1b2c3d4e5f6_seed_member_transactions.py` uses raw parameterized `sa.text()` with `.bindparams()`** — safe (no string interpolation of values), consistent with the project's existing caution around `text()` injection risk (see item 2 in `[[project_transaction_patterns]]`). The lookup `SELECT id FROM user WHERE username = 'member'` hardcodes a literal username match against the `user` table/column names, which is fine since `user.username` is a real unique column, and the migration no-ops gracefully (`if member_id is None: return`) if the seed user doesn't exist (e.g., in a fresh env without the earlier seed-admin/seed-members migrations' data, though those are `down_revision`-chained ahead of this one so it should always exist by the time this runs).
2. **`downgrade()` uses `sa.Table(..., autoload_with=connection)` + a `SEED_MARKER` sentinel description (`"overview-page-seed"`) to selectively delete only migration-inserted rows** — good practice, avoids wiping any real user data with the same username.
3. **Dead dict key**: each row dict in `upgrade()` includes `id=None` which is never used (the INSERT statement's column list excludes `id`, correctly letting the DB autoincrement) — harmless but worth a one-line cleanup if this file is touched again.
4. **`sort_dir` query param** added to `TransactionFilterParams`/`FilterParams` and threaded through `TransactionRepository.get_all` — see item 19 in `[[project_transaction_patterns]]` for the base-class scope-creep note. Correctly validated as `Literal["asc","desc"]` (422 on bogus values, confirmed by test). Good test coverage both at router and service level for asc/desc and the omitted-default case.
5. **Category enum shrink (11→8)** kept backend enum, frontend `types.ts` union, and test fixtures in sync — see item 20 in `[[project_transaction_patterns]]`.
6. **Dataviz charts (`CategoryBarChart.tsx`, `IncomeExpenseTrendChart.tsx`)**: both use `recharts`, custom SVG `<text>` label components keyed off untyped `RechartsLabelProps`/`TooltipContentProps`, CSS-variable-driven theming (`var(--income)`, `var(--expense)`, etc.) rather than hardcoded hex, and `useId()` for collision-safe gradient/filter SVG ids — solid pattern for multiple chart instances on one page. Charts correctly degrade to an empty-state message when their slice of `data` is empty, independent of the page-level `hasTransactions` empty state in `OverviewClient.tsx`.
7. **`OverviewClient.tsx` loading/error/empty state branching is linear and easy to follow** — `isLoading` → skeleton, `isError || !data` → generic error, `!hasTransactions` → empty-state card, else → full dashboard. No dead branches, no overly broad `catch` (uses react-query's `isError` instead).
8. **No service/repository changes needed for the frontend queries** since `/transactions/summary` and sorted `/transactions/` already existed — `web/lib/queries.ts` is a thin, correctly-typed wrapper (`useTransactionSummary`, `useRecentTransactions(limit)`), consistent with the existing `api.get<T>()` pattern from FT-35/36.
9. **Test coverage is thorough on both sides**: router + service tests for `sort_dir` (asc/desc/invalid/omitted), a dropped-category 422 test, and frontend tests for loading/loaded/empty/partial-data states plus two `queries.test.tsx` cases confirming the exact query-string shape sent to the API.

**Why:** First full dashboard feature combining a small backend filter addition with a frontend data-viz buildout; establishes the `lib/queries.ts` + chart-component pattern future dashboard features will likely follow.
**How to apply:** On future chart/dashboard diffs, check for the same empty-state-per-chart + page-level-empty-state split, CSS-variable theming (not hardcoded colors), and `useId()`-scoped SVG defs. On future `FilterParams` subclasses, check whether `sort_dir`/`order_by` additions on the shared base class are actually consumed by all subclasses or just scope creep (see `[[project_transaction_patterns]]` item 19).
