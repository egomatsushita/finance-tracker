# Plan: Frontend Scaffold (FT-34)

Spec: `_specs/frontend-scaffold.md`

## Context
First frontend ticket. Creates `web/` as a standalone Next.js (App Router, TS, Tailwind v4) project with fonts, design tokens, lint config, and env wiring. No auth, no API calls, no real pages — the placeholder home page plus `layout.tsx` already exercise every font/token decision, so a separate `/design` showcase route is redundant and not built. Resolved open questions: commit `web/.env.local.example`, gitignore `web/.env.local`; use Tailwind's `class`-based dark mode strategy now (no toggle UI yet — media-query-driven class application only, toggle control ships in FT-42).

Verified against Context7 during planning (not deferred to implementation): `create-next-app` flags, Tailwind v4's CSS-first `@theme`/`@custom-variant` config, and `next/font/google` usage. Findings baked into the steps below — no separate "check docs" step at implementation time.

## Step 1 — Scaffold the Next.js project
1. From repo root: `npx create-next-app@latest web --typescript --tailwind --eslint --app --import-alias "@/*"` (omit `--src-dir` — its absence is the default, no-`src/` layout; this installs current Next.js with Tailwind v4 by default, confirmed via Context7, so no manual v4 migration is expected).
2. Remove boilerplate Next.js starter content (logo, default page copy) but keep the generated config structure.

## Step 2 — Fonts
1. In `web/app/layout.tsx`, load `IBM_Plex_Sans` and `IBM_Plex_Mono` via `next/font/google`. **Implementation note:** the installed Next.js 16.4.0 / Turbopack build fails on multi-entry `weight` arrays for `next/font/google` ("queries have exactly one entry"). `IBM_Plex_Sans` turned out to expose a true `"variable"` weight axis, so it uses `weight: "variable"`; `IBM_Plex_Mono` has no variable axis, so it keeps `weight: ["400", "500"]`, which built fine (the bug was specific to the combination tried for Sans, not arrays generally).
2. Apply both `.variable` classes on the `<html>` element; wire `--font-ibm-sans`/`--font-ibm-mono` into the Tailwind theme via `@theme inline` in `globals.css` so `font-sans`/`font-mono` utilities resolve to them.

## Step 3 — Color tokens (light/dark)
1. In `globals.css`, define CSS custom properties for each token from `_plans/dashboard.md`'s palette table (ground, surface, ink, muted-text, muted-border, brand-accent, income, expense, highlight) under `:root` (light values).
2. Add a `.dark` class block overriding the same properties with dark values.
3. Per Context7, Tailwind v4 class-based dark mode is enabled with `@custom-variant dark (&:where(.dark, .dark *));` in `globals.css` (replaces v3's `darkMode: "class"` config option). No toggle UI yet, but add a small inline script in `layout.tsx` that reads `prefers-color-scheme` on load and applies/removes `.dark` on `<html>`, plus listens for OS-level `change` events so it flips live without reload. This satisfies "switches via prefers-color-scheme" from the spec while keeping the door open for a manual toggle later (FT-42).
4. Map each CSS property to a Tailwind theme color inside `@theme` (e.g. `--color-ground`, `--color-surface`, `--color-ink`, `--color-brand`, `--color-income`, `--color-expense`, `--color-highlight`) so pages can use `bg-ground`, `text-ink`, etc.
